Problem

Anova shut down the cloud for the original Wi-Fi sous-vide cooker (the 900W "A3"). Anova4All stands in for that cloud: the cooker dials into our server over TCP and the browser controls it. Today it only works for one household, and it is unreliable:

  • Commands get lost or crossed. After one slow reply, every later reply gets matched to the wrong command (seen live as "parse error in GetTimerStatus"). A connection that hits a read error stays "alive" and every command after it times out.
  • The UI lies or goes blank. Live updates on the multi-user branch never arrive: subscribers are keyed by database ID, broadcasts by the cooker's ID card. When the cooker is offline the screen shows an empty °F instead of saying so.
  • Setup fails silently. Bluetooth writes over 20 bytes get cut, so Wi-Fi details arrive truncated. A cancelled scan shows nothing. No screen explains how to get the cooker ready.
  • The multi-user branch (feat/store) can't run. It crashes at startup (two route patterns conflict), crashes on requests (wrong user-ID type), and its database rule lets a user rewrite the ownership and key of their own devices.
  • A finished timer doesn't stop cooking. The cooker only beeps and keeps heating.

Why now: you want other Anova Wi-Fi owners to use it. They need to sign up, set up a cooker without help, and trust that it does what the screen says.

Current state

  • Running today (master, on the Pi): Go server, no login. The browser stores the cooker's ID and key in localStorage and calls /api/devices/:device_id/*. The UI is served from the Pi and from GitHub Pages.
  • Cooker link (pkg/wifi): the cooker connects to TCP 8080. connection.go holds one pending-reply slot with a 10 s timeout. device.go polls 6 commands every 2 s. manager.go tracks devices by ID card.
  • Live updates (internal/rest/sse.go): one goroutine per message per subscriber, no de-duplication, no initial state.
  • Multi-user branch (feat/store): Supabase login in the browser. Go checks Supabase tokens with a shared secret (JWT_SECRET). Postgres through sqlx/lib-pq, schema in init.sql (devices.user_id, RLS). Pairing in internal/store/store.go. Frontend moved to Bun, Tailwind 4 and shadcn, still on React 18.
  • Setup (frontend/src/components/device-setup.tsx, lib/client/ble/*): Web Bluetooth sends server para, wifi para, set number; no chunking; listeners leak on timeout.
  • New Supabase project is live and empty. It signs login tokens with ES256 keys published as a key list (JWKS). The database URL uses the session pooler (IPv4), which the Pi needs.

Outcome: one hosted server that many owners sign up to. Each owner pairs their cooker through a guided setup, shares it with their household by link, and controls it reliably. An optional auto-stop ends cooking when the timer runs out.

Requirements

  • Sign up, confirm email, sign in and reset password, all from the browser through Supabase Auth.
  • A person sees and controls only the cookers they own or were invited to. The database enforces this, not just the UI.
  • Pairing only happens in the browser, next to the cooker. The browser connects over Bluetooth, which only works within a few metres, and writes a fresh key. The server then checks that the live cooker reports that same key. There is no way to pair remotely.
  • Setup has to feel smooth. One guided flow from power-up to cooking. Bluetooth hiccups are retried automatically. A failed step can be retried on its own, without starting over. Every wait shows progress, and every failure names the fix.
  • Owners invite members with a one-time link (expires in 7 days). Members control the cooker; only owners rename, invite, remove members or unpair.
  • Scale: tens of users at most. Prefer the simplest fix that makes connections dependable; no production-scale machinery.
  • Every defect A1–F4 above is fixed, plus G1–G5, each with a test that fails before the fix: a fake TCP cooker for A–B, an SSE harness for C, handler tests for D, a fake GATT characteristic for E. Go tests run with -race.
  • Commands never get crossed. A dead link is noticed within about 6 s and the UI says "Cooker offline". It recovers without a page reload.
  • Setup explains how to get the cooker ready, checks Wi-Fi details before sending them, and tells you which step failed and what to do.
  • Auto-stop is per cook and off by default. When on, the server sends stop at timer end and the alarm keeps sounding. It survives a server restart.
  • Redesigned UI (setup, cook screen, device settings, sign-in, invite), built with the impeccable design process.
  • Compatibility: none. Clean cut-over from master. On deploy you sign up and re-pair the cooker. The Pi keeps a backup of the old build for rollback.

The browser signs in with Supabase and reads its own devices straight from the database, which only returns rows you're allowed to see. For anything live it calls the Go server with the same login token. Go holds the cooker connections, checks your membership, and records ownership and cooks in the database.

Go: auto-stop service

Opens a cook when heating starts and closes it when it stops. Detects timer end from any of: the cooker's "time finish" event, polling (timer was counting down, now 0, still heating), or after a restart the stored deadline has passed. Sends one prioritized stop with retries and records why the cook ended.

Withheld action: Bob tries to unpair or rename

The rpc unpair_device function checks owner inside and refuses. An update devices set name=… matches no row under the owner-only policy, and the UI hides both buttons for members. Bob can still start, stop, and set temperature, timer and auto-stop.

Round trip: Bob starts a 90-minute cook with auto-stop

  1. Bob turns on "Stop cooking when timer ends" (sets the next-cook flag) and presses Start. Go puts the commands at the front of the queue: set timer, start.
  2. The cooker reports it's heating. Go opens a cook, copies auto-stop = on, and stores the deadline. The live stream shows "Stops at 14:30" to Alice and Bob.
  3. The Pi restarts at 13:00. On reconnect Go finds the open cook and keeps watching.
  4. At 14:30 the timer ends (event or poll). Go sends stop with retries, records end reason = timer, and sends "cook ended". The cooker beeps and the UI says "Stopped by timer, alarm sounding" with a Silence button.

Refusal: Eve tries to claim Alice's cooker by guessing

Eve posts pair {id_card: a3-demo0001, key: guess}. Go asks the live cooker for its key. It doesn't match, so Go returns key_mismatch. After 5 tries in 10 minutes (per user, per IP and per device) Go returns rate_limited. Keys are 10 characters of a–z0–9, so guessing is hopeless.

Decisions

Purple yours = your call (already answered unless marked open). Blue mine = technical, decided from the code and docs. Click an option to see its details.

Risks

  • Home IP changes break remote cookers. The cooker stores a raw IP (it can't use DNS names in server para). If your public IP changes, every remote cooker needs setup again. Mitigation: a README note now, a static IP or VM later.
  • Pi 1 B+ capacity. Single core, 512 MB. Fine for dozens of cookers. The server stays stateless apart from the live connections, so a move needs no code change.
  • Supabase free tier. The built-in email sender only sends a few emails per hour, so sign-ups can stall. Add SMTP before going public. The project pauses after a week without activity (live traffic should keep it awake).
  • Pi to Frankfurt latency on every membership check. Hence the short cache, which means a removed member keeps control for up to 15 s.
  • Exact cooker setup steps aren't documented by Anova (manual behind a login). The copy is verified on your cooker before release.
  • Public port 8080 exposes the cooker protocol to the internet. Anyone can connect a fake "cooker". It can only register an unowned ID card and can't control anything.

Behavior changes

  • Everyone must sign in. The open API and the browser-stored cooker key go away.
  • The GitHub Pages UI stops working until it's rebuilt against the new API.
  • The device list comes from Supabase. Only live data comes from the Pi.
  • Pairing always happens in the browser over Bluetooth with a fresh key. The "reset key" checkbox, which skipped pairing, is removed, and nobody can pair remotely or from iOS.
  • A cooker that reconnects with a different key is parked as "unclaimed" until someone re-pairs it (question 1).
  • New: members, invite links, auto-stop, explicit offline state.

Non-goals

  • Supporting other models (Nano, Pro, 3.0, Bluetooth-only 800W).
  • Native apps, or iOS Bluetooth (Safari has no Web Bluetooth).
  • Push notifications, recipes, cook history UI beyond the last end reason.
  • Custom SMTP setup (noted as a step before going public).
  • A legacy no-login mode, or migrating master's localStorage settings.
  • Moving off the Pi.
  • Offering server-side Bluetooth linking to other users. It stays an internal tool (see decision "Server-side linking").

Open questions

1. A cooker reconnects with a different key: what happens to access? yours · decided

Decided: suspend, and restore if the owner re-pairs. Access stays tied to the stored key. A connection with an unknown key is parked as "unclaimed" (same mechanism as G1), and members see "Cooker was set up again — re-pair to control it". If the original key comes back, nothing changes. If the previous owner pairs the new key, the members are kept. If another user pairs it, everyone else is removed. Nobody's access is deleted just because a connection showed up.
